## 3. 项目目标与产品边界

### 3.1 产品愿景

NovelCraft AI 小说创作工作台不是单纯的 AI 续写器，而是面向长篇小说创作的结构化创作系统：

- 用结构化叙事数据库管理人物、关系、情节、时间线。
- 用本地 Markdown 知识库沉淀世界观、素材、文风样例和写作理论。
- 用结构化输入表单替代纯自然语言聊天框，提高 AI 生成的可控性。
- 用上下文记忆机制减少吃书、人设崩坏和跨章节不一致。

### 3.2 当前阶段目标

v0.3 将前 12 周目标定义为：

> 在当前 Windows 本机上交付一个可运行的 AI 小说创作 MVP，支持作品管理、人物管理、章节编辑、知识库浏览、结构化 AI 生成和基础记忆。

### 3.3 非目标

MVP 阶段暂不追求：

- 完整本地离线 AI 写作。
- 全自动一致性审查。
- 多模型全部适配。
- 大规模知识库向量检索。
- 复杂图谱编辑器。
- Word 高保真排版导出。
- 商业级自动更新系统。

## 5. 总体架构设计

### 5.1 分层架构

```text
┌─────────────────────────────────────────────────────┐
│ Vue Renderer                                         │
│ - 页面、表单、编辑器、预览、可视化                    │
│ - 不直接访问 fs / shell / 原生模块                    │
├─────────────────────────────────────────────────────┤
│ Preload API                                          │
│ - contextBridge 暴露窄接口                            │
│ - typed IPC client                                   │
├─────────────────────────────────────────────────────┤
│ Electron Main Process                                │
│ - IPC Handler、窗口生命周期、文件系统、安全边界        │
├─────────────────────────────────────────────────────┤
│ Application Service                                  │
│ - 作品服务、人物服务、章节服务、知识库服务、AI 服务     │
├─────────────────────────────────────────────────────┤
│ Repository / Index                                   │
│ - JSON Repository、Markdown Repository、全文索引       │
│ - 后续扩展 SQLite / Vector Index                      │
└─────────────────────────────────────────────────────┘
```

### 5.2 技术栈

| 层级 | 技术选型 | 说明 |
|---|---|---|
| 桌面框架 | Electron | Windows 本地桌面应用，主进程负责文件与系统能力 |
| 构建工具 | electron-vite | 适合 Electron + Vite + Vue3 + TypeScript |
| 包管理器 | pnpm 11.3.0 | 当前本机已修复，优先使用 |
| 前端框架 | Vue3 + TypeScript | 组件化 UI，类型约束 |
| UI 组件 | Element Plus | 快速搭建管理型界面 |
| 编辑器 | CodeMirror / Markdown 编辑器优先 | MVP 优先保证 Markdown 源文件可靠 |
| 数据校验 | Zod | IPC 入参、JSON 文件、AI 响应校验 |
| 存储 | Markdown + JSON | 人类可读，便于备份和迁移 |
| 搜索 | FlexSearch 或 MiniSearch | MVP 先做全文搜索 |
| AI Provider | 单模型优先 | 先实现一个稳定 Provider，再扩展多模型 |
| 向量化 | ONNX Runtime + BGE-small-zh | Beta/Pro 阶段 Spike 通过后启用 |
| 可视化 | Cytoscape.js / vis-timeline | P1/P2 阶段逐步加入 |

### 6.2 知识库结构

结构：

```text
knowledge_base/
├── _index.yaml
```

### 6.3 存储策略

章节正文优先使用 Markdown 保存：

- 易读。
- 易备份。
- 易导出。
- 便于用户脱离软件访问内容。

章节元数据单独保存到 `chapters_meta/*.json`：

- AI 生成记录。
- 场景状态。
- 段落摘要。
- 用户批注。
- 版本信息。

结构化数据保存为 JSON：

- `characters.json`：人物库。
- `relations.json`：人物关系边。
- `timeline.json`：时间线事件。
- `plots.json`：情节树。
- `memory/*.json`：记忆与摘要。

### 6.4 MVP 保存机制

MVP 不实现复杂差异写入，先实现可靠的原子写入：

```text
1. 读取现有 JSON。
2. 使用 Zod 校验。
3. 修改内存对象。
4. 保存前备份旧文件。
5. 写入 file.tmp。
6. rename 替换原文件。
7. 保存成功后更新内存索引。
```

### 6.5 Git 过滤原则

源码仓库不提交：

- `node_modules/`。
- 构建产物。
- 运行时 workspace。
- knowledge_base 实际内容。
- 模型文件。
- 向量索引。
- 本地环境变量。
- Electron 打包文件。

## 7. 本地知识库方案

### 7.1 知识库目标

知识库用于跨作品复用：

- 世界观设定。
- 人物原型。
- 物品、技能、地名、势力。
- 文风样例。
- 写作理论。

### 7.2 Markdown 格式规范

知识库文档采用 YAML Frontmatter + Markdown 正文：

```markdown
---
kb_id: kb_magic_001
category: worldbuilding
type: system
tags: [magic, cultivation]
---

# 灵力体系

## 核心规则

1. 灵力消耗后需要恢复，禁止无限续航。
2. 属性相克可以被高阶力量逆转，但必须付出代价。
```

### 7.3 MVP 检索策略

MVP 阶段先不依赖向量模型，采用稳定可控的检索方式：

- Frontmatter 精确过滤。
- 标签检索。
- 标题检索。
- 全文搜索。
- 用户手动选择要注入的知识条目。

### 7.4 Beta/Pro 向量化策略

向量化作为增强能力，先做技术 Spike 后再进入主线。

候选方案：

| 模型 | 适用场景 | 备注 |
|---|---|---|
| BGE-small-zh-v1.5 | 中文语义检索 | 更适合中文小说知识库 |
| all-MiniLM-L6-v2 | 英文/通用检索 | 中文效果不如中文模型 |

本机模型目录：

```text
F:/AINovelistData/models
```

向量索引目录：

```text
F:/AINovelistData/knowledge_base/_vectors
```

### 7.5 分块策略

| 知识类型 | 分块方式 | 注入方式 |
|---|---|---|
| 体系化设定 | 按 H2/H3 标题切分 | 作为硬约束注入 |
| 素材条目 | 单个条目一个块 | 作为可选素材注入 |
| 文风样例 | 场景标签 + 正文片段 | 作为 Few-shot 示例注入 |
| 写作理论 | 按方法论小节切分 | 作为创作指导注入 |

## 8. AI 生成与 Prompt Pipeline

### 8.1 结构化输入优先

MVP 采用“导演模式简版”：

| 输入项 | 控件 | MVP 是否需要 |
|---|---|---|
| 写作意图 | 单选 | 是 |
| POV 人物 | 下拉框 | 是 |
| 场景类型 | 单选 | 是 |
| 情绪基调 | 单选 | 是 |
| 节奏控制 | 单选 | 是 |
| 关联情节 | 下拉框 | 是 |
| 强制出场人物 | 多选 | 是 |
| 禁止出场人物 | 多选 | 是 |
| 字数目标 | 数字输入 | 是 |
| 用户补充说明 | 文本框 | 是 |
| 时间锚点 | 时间线选择器 | Beta |
| 风格样例 | 知识库选择 | Beta |
| 伏笔/秘密控制 | 多选开关 | Beta |

### 8.2 Pipeline 结构

统一命名为四阶段：

```text
Analyzer → Fetcher → Builder → Injector
```

| 阶段 | 输入 | 输出 |
|---|---|---|
| Analyzer | WritingRequest | ContextRequirements |
| Fetcher | ContextRequirements | ContextBundle |
| Builder | ContextBundle + 模板 | PromptDraft |
| Injector | PromptDraft + Token 预算 | FinalPrompt |

### 8.3 TypeScript 接口草案

```ts
interface WritingRequest {
  intent: 'continue' | 'rewrite' | 'expand' | 'outline_branch' | 'scene_script'
  povCharacterId?: string
  sceneType: 'dialogue' | 'action' | 'description' | 'transition' | 'monologue'
  mood: 'tense' | 'relaxed' | 'sad' | 'joyful' | 'mysterious' | 'violent'
  pacing: 'fast' | 'normal' | 'slow'
  requiredCharacterIds: string[]
  bannedCharacterIds: string[]
  plotId?: string
  targetWords: number
  userNote?: string
}

interface LLMProvider {
  generateText(request: GenerateTextRequest): Promise<GenerateTextResult>
  streamText(request: GenerateTextRequest): AsyncIterable<GenerateTextChunk>
  countTokens?(text: string): Promise<number>
}
```

### 8.4 MVP Prompt 组成

MVP Prompt 只保留最关键上下文：

1. 系统身份。
2. 写作意图。
3. POV 限制。
4. 当前人物卡。
5. 当前章节摘要。
6. 最近章节摘要。
7. 硬约束记忆。
8. 用户补充说明。
9. 输出要求。

### 8.5 多模型策略

MVP 只实现一个模型 Provider，但代码保留扩展接口。

建议优先顺序：

1. 选择一个稳定的云端文本模型作为 MVP Provider。
2. 实现流式输出。
3. 增加 token 预算估算。
4. 再接入第二个 Provider。
5. 最后支持 Ollama 或本地模型。

## 9. 上下文记忆机制

### 9.1 分阶段实现

| 记忆层级 | v0.3 阶段 | 说明 |
|---|---|---|
| 短期记忆 | MVP | 当前会话用户偏好、刚生成内容 |
| 章节记忆 | MVP | 当前章节摘要、场景状态 |
| 长期记忆 | Beta | 定稿章节摘要、人物状态变化 |
| 工作记忆 | MVP 简版 | 用户确认的硬约束 |
| 自动一致性审查 | Pro | AI 辅助检测，不承诺完全自动 |

### 9.2 硬约束记忆

`memory/hard_constraints.json`：

```json
{
  "constraints": [
    {
      "id": "rule_001",
      "type": "appearance",
      "content": "林深右手有疤，不是左手",
      "priority": "critical",
      "source": "user"
    },
    {
      "id": "rule_002",
      "type": "secret",
      "content": "char_003知道真凶身份，但char_001还不知道",
      "priority": "critical",
      "source": "user"
    }
  ]
}
```

### 9.3 章节摘要

每章定稿后，由 AI 生成摘要，用户确认后保存：

```json
{
  "ch_001": {
    "abstract": "林深接到化工厂爆炸案，初步调查发现死者身份存疑。",
    "key_events": ["evt_001"],
    "characters": ["char_001", "char_003"],
    "open_threads": ["死者真实身份尚未揭露"],
    "confirmed_by_user": true
  }
}
```

### 9.4 记忆注入原则

- 硬约束永远优先注入。
- 章节摘要按相关性和时间临近注入。
- 未经用户确认的 AI 摘要不得作为强约束。
- 自动提取结果必须允许用户编辑和删除。

## 10. 可视化与交互设计

### 10.2 可视化优先级

| 功能 | 阶段 | 实现方式 |
|---|---|---|
| 人物列表 | MVP | 表格 + 卡片 |
| 人物详情 | MVP | 表单页 |

### 10.3 编辑器策略

正文源文件使用 Markdown。

MVP 推荐优先评估：

1. CodeMirror + Markdown 预览。
2. Milkdown。
3. TipTap Markdown 模式。

决策原则：

- Markdown 往返不能破坏正文。
- 自动保存实现简单。
- 大文件编辑性能可接受。
- 后续可插入 AI 生成片段。

## 11. Electron 安全与工程规范

### 11.1 安全默认值

Electron 窗口必须使用安全配置：

```ts
webPreferences: {
  contextIsolation: true,
  nodeIntegration: false,
  sandbox: true,
  preload: preloadPath
}
```

### 11.2 IPC 规范

- Renderer 不直接访问 `fs`。
- Renderer 不直接访问 `ipcRenderer`。
- Preload 只暴露窄 API。
- 主进程校验所有 IPC 参数。
- 所有文件路径由主进程解析和限制。
- 不允许 Renderer 传入任意绝对路径执行读写。

### 11.3 Markdown 与 AI 输出安全

- Markdown 预览必须防 XSS。
- 禁止直接渲染未经清洗的 HTML。
- AI 输出按普通文本处理，除非明确进入受限 Markdown 渲染流程。
- 外部链接打开前需用户确认。

### 11.4 工程规范

- 使用 `vue-tsc --noEmit` 做类型检查。
- 使用 ESLint / Prettier 保持格式一致。
- 所有 Repository 层写入需要测试。
- 所有数据 Schema 需要版本号。
- 数据迁移脚本必须可重复执行。
- 大文件、模型、缓存和运行时数据不得提交到 Git。

## 13. 技术风险与应对策略

| 风险 | 影响 | 阶段 | 应对策略 |
|---|---|---|---|
| JSON 文件损坏 | 丢稿 | MVP | 原子写入、备份、Schema 校验 |
| Markdown 编辑器往返损失 | 正文格式异常 | MVP | 明确 Markdown 为源文件，限制复杂富文本 |
| Electron 安全边界不清 | 本地文件风险 | MVP | preload + typed IPC + 参数校验 |
| AI 输出不可控 | 人设崩坏、吃书 | MVP | 结构化 Prompt + 硬约束 + 用户确认记忆 |
| 多模型差异大 | 适配复杂 | MVP/Beta | 先实现单 Provider，接口预留 |
| ONNX 打包失败 | 本地检索不可用 | Beta/Pro | 独立 Spike，不阻塞 MVP |
| 向量检索效果不佳 | 推荐素材不准 | Beta/Pro | 保留标签/全文搜索作为基础路径 |
| Node 22 原生依赖兼容 | 安装失败或运行异常 | Beta/Pro | 准备 Node 20 LTS 备选环境 |
| VS Build Tools 环境变量未加载 | 原生模块构建失败 | Beta/Pro | 使用 node-gyp 自动定位或加载 VS 开发环境 |
| 可视化性能问题 | 图谱卡顿 | Beta/Pro | 限制同屏节点、懒加载、只读优先 |
| Word 导出复杂 | 交付延期 | Pro | MVP 只做 Markdown/TXT 导出 |
| 自动一致性审查不可靠 | 用户误信错误结果 | Pro | 标注为 AI 辅助建议，用户确认后生效 |

## 结论

v0.3 将项目计划从“可落地路线”进一步推进为“基于本机环境的可执行计划”。

当前状态：

```text
环境准备已完成 → 可以初始化项目脚手架 → 优先打通安全 Electron 架构与本地数据保存 → 再进入 AI 生成闭环
```

推荐执行顺序：

```text
pnpm + electron-vite → main/preload/renderer 安全边界 → F 盘 workspace → JSON/Markdown Repository → AI 生成闭环 → 基础记忆 → ONNX Spike
```

该路线能降低本机开发、依赖安装、磁盘空间和原生模块构建风险，同时保留长期扩展到本地 RAG 与高级可视化的空间。
